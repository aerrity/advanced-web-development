01 / THE ASSIGNMENT

Your own case study

You will design and build a Laravel web application for a case study of your own choice, working on it across the whole 12 weeks of the module.

The Book Reviews application and its tutorial notes are your worked example. They show you, step by step, how to build each part of a Laravel application.

You do not submit Book Reviews. Apply each technique from the tutorial to your own case study.

Module aim and learning outcomes

The aim of this module is to improve your knowledge and skills in relation to the development and testing of web applications, and provide you with the understanding, skills and competencies to use server-side web application frameworks.

  1. LO1 — Explain the principles of server-side Web Application Frameworks
  2. LO2 — Design, develop, test and debug a web application using a server-side web application framework
  3. LO3 — Document, explain and defend the design and implementation of web applications

Your case study must include

  • A main entity, the “thing” your application is about (equivalent to a Book in Book Reviews)
  • At least one one-to-many (1:M) relationship, e.g. one Book has many Reviews
  • At least one many-to-many (M:N) relationship, e.g. Books and Authors
  • At least two roles, with some pages accessible only to users with a given role
RequirementBook Reviews example
Main entityBook
1:M relationshipA Book has many Reviews
M:N relationshipA Book has many Authors, and an Author has many Books (author_book join table)
RolesOnly admins can create, edit and delete Books and Authors. Users can only edit and delete their own Reviews.

Extensions

Once your core application is working, you can earn further marks at Assessment Point 2 by adding features beyond what the Book Reviews tutorial covers. The examples below are indicative, not an exhaustive list. You can explore other extension ideas in the Learning Lab’s Advanced Extensions section after completing the core application.

  • Image uploads with resizing or validation
  • Pagination and sorting on index pages
  • An admin dashboard showing summary statistics
  • A further relationship or entity
  • Email notifications

Discuss any extension with your lecturer before you build it, so you both agree it is feasible and worthwhile. Finish the core requirements first: an extension will not make up for missing core functionality.

02 / TECHNICAL REQUIREMENTS

What your app must use

  • Laravel 12 with Blade views, no Livewire, Inertia, React or Vue
  • Laravel Breeze (Blade stack) for registration and login
  • MySQL in the Docker environment provided with Book Reviews
  • Eloquent models and relationships, no raw SQL
  • Migrations, factories and seeders; php artisan migrate:fresh --seed must build realistic demo data
  • Resource controllers and route model binding
  • Laravel validation for all form input
  • Passing PHPUnit tests using php artisan test

Using AI tools

You may use AI tools to understand errors and fix bugs. We recommend writing your own code so you develop the skills and understanding to build the application independently. If you use AI-generated code, you must be able to explain every line, and record your AI use for the final design document.

03 / ASSESSMENT

How your work is assessed

  1. Your application code in your classroom50.org repository; include only your own case study
  2. Your Git commit history, with regular meaningful commits throughout the module
  3. A recorded screencast, uploaded to the OneDrive folder created for you
  4. Your attendance and observed progress in class
  5. A viva, a short one-to-one discussion of your code, which gates your marks

The viva

During scheduled class hours, you will trace one or two requests through your application, for example submitting an edit form. Explain what happens at each stage:

Route → Middleware → Controller → Validation → Model / relationships → Database → Response

You will have your code open. You do not need to memorise it, but you do need to understand it. A time slot will be published in advance.

05 / ASSESSMENT POINT 2 · 70%

Final submission

Code + screencast: 23:59, Friday 11 December 2026. Viva: Tuesday 15 December 2026.

What we expect

A complete application covering Lessons 1–6 of Book Reviews, plus role-based authorisation, applied to your own case study.

Deliverables

  1. Your classroom50.org repository showing regular commits across all 12 weeks, including full CRUD on your main entity, CRUD on other entities where needed, M:N relationships managed through forms, search on the main entity, role-based authorisation for at least two roles, any agreed extensions, passing tests, and a final design document in docs/
  2. A screencast of maximum 10 minutes in OneDrive demonstrating all features as each role, passing tests and main design decisions

We suggest using role middleware, as demonstrated in class. You may use a different approach if you explain and justify your choice in your design document.

Design document

Keep this concise. Include the following nine sections as a PDF or Markdown file in docs/. Write this document in your own words. Describe your own work, decisions and understanding rather than copying explanations from the tutorial, documentation or AI-generated text. The word counts are maximums per section, not targets. Aim for approximately 900 words or fewer overall, excluding your ERD, route table and code snippets.

  1. Case study max 75 words: what your application does and who uses it.
  2. Database design max 125 words: include an ERD and explain the main tables, relationships, constraints and design choices.
  3. Routes max 50 words: provide a table showing HTTP method, URI, controller action and middleware, with any brief notes needed.
  4. How a request is handled max 125 words: trace one real request through your application, from route to response.
  5. Authorisation max 100 words: identify your roles, permissions, enforcement and why you chose this approach.
  6. Testing max 100 words: what you tested, why, and anything you deliberately did not test.
  7. Extensions max 75 words: describe any additional features and how they work. If none, say so briefly.
  8. AI Agent Use max 100 words: name tools used, give specific examples of prompts and responses, explain what you did with the output, and reflect on when AI helped or misled you. If you did not use AI, state this.
  9. Reflection max 150 words: what went well, what you would improve and any known problems.

Use diagrams, route tables and short code excerpts where useful. Focus on explaining your own decisions, not describing Laravel in general.
